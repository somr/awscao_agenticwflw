## Problem statement

Payment providers may redeliver the same callback — identified by a stable `provider_event_id` — more than once: for a genuinely new event, for an event whose processing already completed, for an event whose processing is still in flight on a concurrent request, and for an event whose prior attempt failed after being claimed but before completion. Today `PaymentService.process_callback()` (`app/payment_service/payment_service.py:23-27`) discards the boolean return of `PaymentRepository.record_if_new()` and unconditionally calls `FulfilmentService.fulfil()` on every callback, so a repeated `provider_event_id` always re-fulfils (AC-1/FR-1 violated — confirmed failing test `test_duplicate_callback_does_not_refulfil`), there is no way for a failed-then-retried event to re-claim its ID (FR-2 entirely unimplemented — `repository.py` has no release/delete method), and the log line is identical regardless of duplicate status (AC-3 violated — confirmed failing test `test_duplicate_is_distinguishable_in_logs`).

This plan makes callback processing idempotent by: (a) gating fulfilment on the existing `PRIMARY KEY` uniqueness constraint on `provider_event_id` in `processed_callbacks` — the constraint itself remains the sole concurrency-safe "claim vs. duplicate" gate, per C-1/C-2 (no application lock, no distributed lock); (b) adding a delete-then-reinsert release mechanism so a failure after claim (per FR-2's now-explicit definition) frees the row for a later retry to re-claim through that same constraint, never via a mutable-status compare-and-swap, per C-4; (c) emitting a distinguishable duplicate-vs-first log message (AC-3); and (d) documenting and testing `PaymentRepository`'s per-request construction discipline (C-5) so a genuine concurrent-duplicate scenario (FR-3) is exercised against real constraint contention rather than in-process serialization. The external response contract (`{"status": "ok", "payment_id": ...}`) is left untouched, preserving AC-2/FR-4 by construction — `CallbackController.handle()` never branches on processing outcome today and this plan does not change that.

## Scope

### In scope
- `app/payment_service/repository.py` — add a release-for-retry method (delete-then-reinsert pattern) using the existing `PRIMARY KEY` constraint and schema; no schema/column change, and no new read/introspection method (row-presence is verified indirectly via `record_if_new()`'s existing return value — see FR-2 row and D6). - `app/payment_service/payment_service.py` — gate `fulfil()` on the persistence claim result, add a failure-handling path around the claimed-fulfilment call that releases the claim for retry, and emit a distinguishable duplicate-vs-first log line.
- `app/payment_service/callback_controller.py` — verification only; confirmed by design to require no code change (see Proposed design).
- `app/payment_service/fulfilment_service.py` — no production change; used only as the thing whose failure is simulated by a test-only mechanism for FR-2 coverage.
- `app/tests/test_payment_service.py` — new/extended coverage for FR-1 (already-completed event), FR-2 (failure-then-successful-retry, verified via the `record_if_new()`-based reclaim probe — see FR-2 row), FR-3/FR-4/C-5 (genuine concurrent duplicate via independently constructed `PaymentRepository` instances against the same store, synchronized to force real overlap — see T5), on top of making the two already-encoded, currently-failing tests (`test_duplicate_callback_does_not_refulfil`, `test_duplicate_is_distinguishable_in_logs`) pass.

- Introducing a real PostgreSQL dependency; SQLite remains the accepted stand-in for this repository baseline (per validated context scope).
- Automatic reconciliation/timeout recovery for a crash between "callback accepted" and "outcome durably recorded," leaving that event permanently unresolved with no automatic recovery — accepted known limitation per validated context scope, candidate for a follow-up ticket.
- Automatic recovery of a payment left stuck because a rejected in-flight duplicate was acknowledged successfully while the original claimant's processing later fails and is released for retry (so no further callback for that event can ever arrive) — accepted known limitation per validated context scope, candidate for a follow-up reconciliation-job ticket.
- Building an HTTP/WSGI entrypoint, request-thread pool, or provider-facing transport layer. None exists in the repository baseline and none is requested by the validated context. Where "concurrent request contexts" must be exercised for FR-3/C-5, this plan uses in-process `threading.Thread`s, each constructing its own `PaymentRepository` against the same SQLite file, not a new server layer.

- Refactoring `app/tests/test_payment_service.py`'s existing `setUp` to construct a fresh `PaymentRepository` per test method call. That shared-instance pattern is used only for strictly sequential calls within a single test (no concurrent access), so it does not itself trigger the race C-5 is protecting against; only the new dedicated concurrency test needs, and gets, independently constructed repository instances.
- Making the busy-timeout/WAL hardening itself configurable/toggleable at test time (e.g. a flag to disable it in CI to prove the failure mode). The one-time manual verification described in T5 is a development-time confirmation step, not a permanent CI-exercised code path, so as not to introduce test-only production-code branching. (Round-2 review's `PLAN-003`: this is an accepted, non-blocking tradeoff, not a gap requiring a plan change.)
- Adding a row-existence/count read method to `PaymentRepository`. The round-2 review (`PLAN-001`) confirmed this is not required: FR-2's post-retry verification is achievable indirectly using only `record_if_new()`, which this plan already adds/keeps in scope (see FR-2 row and D6). Adding a query capability that no acceptance criterion, functional requirement, or constraint calls for would be scope creep beyond what the validated context requires.

- **D5 — a fulfilment-failure re-raises uncaught, after `release_for_retry()` runs.** No source text (`CONF:4812`'s functional requirements or `CONF:4934`'s constraints) specifies what should happen to the in-flight caller/response when fulfilment fails; only that the claim must be released. ## Proposed design

The `processed_callbacks(provider_event_id TEXT PRIMARY KEY, payment_id TEXT NOT NULL)` schema is unchanged. The `PRIMARY KEY` constraint remains the single idempotency primitive, exactly as C-1 requires ("the constraint check itself is the concurrency-safe idempotency guarantee").

**Repository (`PaymentRepository`, `app/payment_service/repository.py`):**
- `record_if_new(provider_event_id, payment_id) -> bool`: unchanged. `True` = this call just claimed the ID (first delivery, or first attempt after a released failure). `False` = `IntegrityError`, i.e. a duplicate — either already-completed or currently in-flight; both must be treated identically by the caller (do not fulfil, log as duplicate, return the standard success shape). This existing method also doubles as the read-side proof for FR-2's post-retry test assertion (see D6) — no separate read method is added.
- New `release_for_retry(provider_event_id) -> None`: `DELETE FROM processed_callbacks WHERE provider_event_id = ?` + `commit()`; idempotent (a no-op if the row is already gone). This is the "release" half of C-4's delete-then-reinsert pattern; the "reinsert" half is simply a later, ordinary call to `record_if_new()` for the same ID — no separate write path is introduced for retries.
- `__init__`'s connection construction is hardened for concurrent-writer behaviour under SQLite (an explicit busy-timeout and `PRAGMA journal_mode=WAL`) so that two genuinely concurrent `INSERT`s against the same on-disk file reliably resolve via the `PRIMARY KEY` constraint (one succeeds, one raises `IntegrityError`) rather than intermittently surfacing `sqlite3.OperationalError: database is locked`. This configures SQLite's own concurrency control and does not conflict with C-1/C-2 — it introduces no lock code of any kind.
- Docstring/comment states the per-request construction contract (C-5): one instance/connection per incoming callback request; never share one instance across concurrent requests.
- **No row-count or row-existence read method is added** (round-2 review `PLAN-001`, resolved via D6): FR-2's test proves row presence using only `record_if_new()`'s existing boolean return, keeping `PaymentRepository`'s public surface unchanged apart from `release_for_retry()`.

**Orchestration (`PaymentService.process_callback`, `app/payment_service/payment_service.py`):**
1. `claimed = self._repository.record_if_new(event.provider_event_id, event.payment_id)`
2. If not `claimed`: log a distinct duplicate message (e.g. `"duplicate callback ignored for provider_event_id=%s"`) at INFO and return `ProcessingResult(payment_id=event.payment_id, fulfilled=False)` — no exception, no side effect. This single branch satisfies AC-1, AC-3, FR-1, and FR-3 together, since `record_if_new()` returning `False` is the one signal that covers both "already completed" and "currently in flight."
3. If `claimed`: call `self._fulfilment_service.fulfil(event.payment_id)` inside a `try`. On any exception: call `self._repository.release_for_retry(event.provider_event_id)`, log the failure, and re-raise the original exception unchanged (see D5 — there is no HTTP/transport layer in this repository to translate the exception into a response, and adding one is out of scope). This satisfies FR-2/C-4.
4. On success: log the existing first-delivery/successful-retry message at INFO and return `ProcessingResult(payment_id=event.payment_id, fulfilled=True)`.

**Controller (`CallbackController.handle`):** unchanged. It reads only `result.payment_id`, never `result.fulfilled`, so the response body is identical across the claimed, completed-duplicate, and in-flight-rejected-duplicate cases by construction — satisfying AC-2/FR-4 without new branching logic in the controller.

**FR-2 test verification technique (T4) — revised per `PLAN-001` in `review-r2-c1.json`:**
- The test-only fulfilment stub raises on its first invocation for a given `provider_event_id` and succeeds on a second (simulating the "claimed, then failed, then retried" scenario).
- After the successful retry, the test asserts `fulfilment_count(<event-id>) == 1` (proving fulfilment ran exactly once across the failed attempt and the successful retry, not twice and not zero).
- The test then calls `repository.record_if_new(<event-id>, <payment-id>)` a **third** time for the same `provider_event_id` and asserts it returns `False`. Since a row can only cause `record_if_new()` to return `False` when it is present, and the `PRIMARY KEY` constraint guarantees at most one row per `provider_event_id`, this conclusively proves exactly one row exists post-retry — without needing any new read/introspection method on `PaymentRepository` (D6).

**Concurrency test design for FR-3/FR-4/C-5 (T5) — unchanged from round 2, carried forward:**
- Each of the two worker threads constructs its **own** `PaymentRepository(db_path)` instance *inside its own thread's target function* (not constructed in the main thread and handed in), because `sqlite3` connections default to `check_same_thread=True` and a connection used outside its constructing thread raises `ProgrammingError` (round-1 review `PLAN-003`).
- Both threads block on a shared `threading.Barrier(2)` immediately before calling `process_callback`/`handle`, so neither can proceed until both have reached the barrier — this forces the two `record_if_new()` `INSERT` attempts to genuinely overlap in time rather than merely being scheduled close together by chance (round-1 review `PLAN-001`). This barrier is the actual, load-bearing overlap-forcing mechanism.
- Each thread records its own wall-clock start/end timestamps around the `handle()` call; the test asserts the two measured intervals overlap (thread A's start precedes thread B's end and vice versa), as corroborating evidence of real concurrent contention. Per round-2 review `PLAN-002` (ADVISORY, non-blocking): this timing assertion is weaker proof than the barrier alone, since the winning thread's interval also spans its `fulfil()` call and can be arbitrarily longer than the losing thread's near-instant rejected-duplicate return, so the assertion can pass even without genuine `INSERT`-level overlap. The barrier's forced-rendezvous semantics remain the actual guarantee; the timing assertion is retained as an inexpensive corroborating check, not the primary correctness argument, and no plan change is required for this to be sound.
- The test asserts `fulfilment_count("<event-id>") == 1` (FR-3) and that both threads' returned responses equal `{"status": "ok", "payment_id": ...}` (FR-4/AC-2).
- **One-time development-time verification (documented, not part of the automated/CI test):** when T1 and T5 are implemented, the developer manually and temporarily removes the busy-timeout/WAL configuration added in T1 and reruns T5 in a loop (e.g. 20–50 iterations) to confirm it becomes flaky with `sqlite3.OperationalError: database is locked`, then restores the hardening. This confirms the mitigation is load-bearing rather than redundant, and is recorded as a one-line comment/commit note next to the hardening code (not as a toggleable code path — see "Out of scope" — so no test-only production branching is introduced). Per round-2 review `PLAN-003` (ADVISORY, non-blocking): this is a one-time manual check, not an automated regression guard against future hardening removal; no plan change is required to proceed, and a future ticket may reconsider whether an ongoing automated signal is warranted.

This design introduces no new dependency, no schema migration, and no lock service, keeping the entire idempotency guarantee inside the existing persistence layer as C-1/C-2/C-3/FR-3 require. The `threading.Barrier` and timing assertions added to T5 are test-only synchronization to *force and prove* real overlap; they are not a production coordination mechanism and do not weaken C-1/C-2.

## Risks and compatibility / rollout considerations

- **SQLite concurrency characteristics differ from PostgreSQL.** Without configuration, two genuinely concurrent `INSERT`s against the same on-disk SQLite file can raise `sqlite3.OperationalError: database is locked` instead of cleanly resolving to one success + one `IntegrityError`, which would surface as an uncaught exception rather than a clean duplicate-rejection under FR-3. Mitigated by T1's busy-timeout/WAL configuration; T5's barrier-forced overlap is specifically designed so this test actually exercises that contention rather than passing incidentally due to scheduling. If T5 still shows flakiness under genuine overlap, treat any residual `OperationalError` as a defect to fix in T1's connection configuration, not as grounds to add a lock service (which C-2 forbids).
- **No structural production enforcement of C-5.** Nothing in the codebase can prevent a future caller from sharing one `PaymentRepository` instance across concurrent requests, since no production request entrypoint exists in this repository to enforce the per-request-construction discipline against. This plan documents the contract (T1) and demonstrates it via the dedicated, synchronization-forced concurrency test (T5), but a future integration/entrypoint layer must re-verify this discipline when it is built — that is out of scope here.
- **No production failure mode exists for `fulfil()` today.** FR-2 verification necessarily depends on a test-only stub/subclass to make fulfilment fail on demand. This plan keeps that mechanism confined to the test file so it cannot mask a real defect in how `PaymentService` handles an exception raised mid-fulfilment; `payment_service.py`'s exception handling is exercised against a real `Exception`, not a special test-only exception type.
- **Shared-file concurrent-edit risk in task execution.** T4 and T5 both modify `app/tests/test_payment_service.py`; executing them as simultaneous, independently-branched edits risks lost work or merge conflicts. Mitigated by sequencing T5 strictly after T4 (see "Parallelisation notes"); T3, which touches a different file, remains safely parallel.
- **`sqlite3` same-thread restriction.** A `PaymentRepository`/connection must be constructed inside the thread that will use it; T5's design states this explicitly to prevent a `ProgrammingError` pitfall during implementation.
- **FR-2 test-verification technique relies on an existing schema invariant, not a new capability.** The `record_if_new()`-returns-`False` reclaim probe (D6) is conclusive only because `provider_event_id` is, and remains, a `PRIMARY KEY` (at most one row per ID). If a future change ever altered that constraint, this test's proof would need to be revisited — flagged here so the invariant's importance to test correctness, not just production correctness, is visible.
- **No schema migration is required** by this design (no status column added, no new column for row introspection), so there is no data-migration risk beyond the synthetic test fixtures already in the repository.
- **Backward compatibility:** `CallbackController`'s public response shape and `PaymentRepository.record_if_new()`'s existing signature/semantics are both preserved unchanged; only a new repository method (`release_for_retry`) and internal `PaymentService` logic are added, so no caller outside this repository is affected. AC-2's "external HTTP response contract" is represented in this repository solely by `CallbackController.handle()`'s Python return-value shape, since no HTTP/WSGI transport layer exists at this baseline; this plan preserves that shape exactly.
- **Rollout:** no feature flag or phased rollout is warranted — this is a single-service demo fixture with no external consumers beyond the existing test suite; deploy as a single change once T6 passes.
- **Known accepted limitations (unchanged by this plan, per validated scope):** a crash between "callback accepted" and "outcome durably recorded" leaves a permanently-claimed, never-fulfilled row with no automatic recovery; a rejected in-flight duplicate that is acknowledged successfully while the original claimant's processing later fails can leave that payment permanently unresolved if the provider never resends the event. Both are explicitly out of scope for PAY-DEMO-001 and are candidates for a follow-up reconciliation-job ticket.
- **Interpretive choice on failure-signaling (D5):** a fulfilment failure re-raises uncaught after the claim is released. This is deliberate for the no-transport-layer baseline, not an oversight, and must be explicitly revisited when/if an HTTP entrypoint is added in a future ticket.
- **Interpretive choice on FR-2 test-verification mechanism (D6, per round-2 review `PLAN-001`):** row presence is proven indirectly via `record_if_new()` rather than via a dedicated read method. This is deliberate to keep `PaymentRepository`'s surface minimal and matched to what the validated context actually requires, not an oversight; a future ticket that needs direct row introspection for other reasons may add such a method then, re-justified against its own requirements.
- **Scope-creep risk:** FR-2/C-4's retry handling is adjacent to the two out-of-scope reconciliation scenarios above; T2's design deliberately does nothing beyond "release on failure, let a future callback reclaim" — it adds no timers, background jobs, or reconciliation logic.
